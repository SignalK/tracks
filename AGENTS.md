# SignalK/tracks

Track accumulation for Signal K: vessel positions kept in memory or in SQLite, plus the HTTP track API that serves them.

These guidelines are written for AI coding assistants, but they apply equally to human contributors. Where something looks overly specific, it's a guardrail for AI tools — humans should use judgment and follow the spirit.

## One package

The repo publishes a single package, `@signalk/tracks-plugin`: the position accumulator, the plugin, the API routes, and a client-side `TrackAccumulator`.

It was formerly two — a `module/` workspace publishing `@signalk/tracks` plus a four-line root wrapper — which is why the tag list carries historical `m<version>` tags alongside `v<version>`. Only `v*` tags are cut now.

The package is **ESM only** (`"type": "module"`) and ships `dist/` plus the webapp's `public/`.

## Build and test

```bash
npm ci
npm run build      # vite library build -> dist/index.js, trackStoreWorker.js + index.d.ts
npm test           # vitest; global setup builds the worker entry first
npm run test:watch # rebuilds the worker before each rerun
npm run test:e2e   # real signalk-server + real QuestDB; its own CI job
npm run typecheck  # tsc --noEmit (also run inside the build, via vite-plugin-checker)
npm run lint       # eslint flat config
npm run format     # prettier --write
```

The unit runner builds the production worker entry into ignored `.vitest-worker/`
before a run and before watch reruns, without the full declaration/typecheck
build. Worker dependencies trigger a full rerun because Vitest cannot see across
the thread boundary. Direct `vitest` invocation also runs this setup. Production
packaging still uses `npm run build` and must be smoke-tested from the tarball.

**`npm run test:e2e` needs a `signalk-server` to boot.** It packs the plugin with
`npm pack`, installs the tarball into a throwaway config dir, boots a real server against it,
and feeds positions as deltas over the WebSocket API. That covers what the unit suite mocks:
that the server can resolve and load the package at all (the `main`-vs-`exports` trap above),
that `signalKApiRoutes` mounts where it should, and that deltas reach the plugin through the
real streambundle.

Point `SIGNALK_SERVER_DIR` at a checkout, default `~/dev/xxx_signalk-server`, built first with
`npm run build:all`, or at an installed package's `node_modules/signalk-server`. CI does the
latter, against the oldest release with the v2 Track API and the newest.

The second tier installs **signalk-questdb** into that server and exercises the history
import through `getHistoryApi()` for real. Test the History API contract, not a provider's storage: how
questdb, influx or anything else keeps its rows is its own business, and a test asserting that
would fail on a provider change that this plugin is unaffected by. It skips itself when nothing
answers at `QUESTDB_URL` (default `http://localhost:9000`), so the server tier still runs
without it. A skipped test there counts as passed, so `QUESTDB_REQUIRED` makes a missing
QuestDB fail the run instead; CI sets it and runs QuestDB as a service container.

`tsconfig.json` extends `@tsconfig/node24`, the same base `signalk-server` uses, so both agree on
which built-ins exist rather than drifting apart. Two options are overridden deliberately: that base
sets `module: nodenext` and `moduleResolution: node16` for a Node-resolved application, while this
package is bundled by vite and needs `ESNext`/`bundler`.

Note the tsconfig target governs type checking only — `vite.config.ts` down-levels the shipped
`dist/` to `node20.19` independently, so raising the base does not raise what the published package
requires. `engines.node` is the field that says that.

On top of the base, `tsconfig.json` is strict and then some — `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitReturns`, `noUnusedLocals`. Keep them on; they caught real bugs when they went in.

Vite transpiles without type checking on its own, so the build runs `tsc` through
`vite-plugin-checker` and fails on the first error — **`npm run build` passing does mean the
types are sound.** `npm run typecheck` is still the quick way to check them without
building, and CI runs it separately. The checker is skipped under vitest, where a type
error in an unrelated file should not stop the suite.

## Architecture

- **Storage is always SQLite.** `start()` builds an `AsyncTrackStore`; its worker owns a `SqliteTrackStore` in the plugin's data directory, so tracks survive a restart with no other plugin involved; without a data directory it reports why and does not start. There is no in-memory alternative and no `source` setting — a track recorder that forgets everything on restart is not worth starting. `TrackAccumulator` remains as the exported client-side helper, not as plugin storage.
- **A position names its vessel by an id.** The tables with a row per position (`BY_CONTEXT_ID`: `positions`, `binned_positions`, `significant`, `level_visits`) hold a `context_id` that `contexts` resolves, since the context's 40-odd bytes of text in them and their indexes were nearly half the file; the small tables kept per vessel keep its name. The store maps between the two in memory (`idOf`, `idFor`, `nameOf`), loads the map again after a rolled-back transaction, and binds `NO_CONTEXT` for a vessel it has no id for, which matches no row, as an unknown name did. A list of vessels comes in the order of their names, as the index on the name gave it before. `prune()` drops the ids nothing refers to any more (`forgetContexts()`), and `AUTOINCREMENT` keeps an id from ever being given to another vessel. `PRAGMA user_version` holds `SCHEMA_VERSION`, and a file a newer version wrote is refused. `migrate()` rewrites a database whose `positions` still has a `context` column, whatever its version says (a new file set up only in part has none), into a new file beside the one a link points to, and renames that over it, having first taken the old one out of WAL mode, so that no log is ever replayed into the new file. Another change to these tables needs a step of its own there, and an older version cannot read the file afterwards.
- **Queries read the store alone; a history provider is read only by the history import.** v1 and v2 answer from the sqlite store, and nothing in a read asks `getHistoryApi()`, so a query never waits for a provider and the store's indexes decide what it costs. What a provider holds of the own vessel reaches the store once, through the history import below. Reads used to reconcile with a provider per query; do not bring that back, since it made every box query pay for a provider read the store could answer, and the store's indexes cannot speed up a provider. **The plugin must stay fully functional with no history provider installed**; see `docs/history-and-storage.md`.
- **The history import copies the own vessel's track from a provider into the store, once.** The webapp starts it (`historyImport.ts`, `/plugins/tracks/history-import`, admin-only). It reads a UTC day at a time, at one-second buckets where a ten-minute probe found positions, and fills only the gaps the store leaves (`fillGaps`); a gap still open at midnight carries into the next day as `inGap`. Deleted spans stay out. Both are judged again inside the commit, since a GPX import, a restore or a delete can land while the provider is read. Each day commits with its progress in `history_imports`, and the progress moves on only once written, so a restart resumes. Nothing is binned.
- **v1 and v2 are different purposes, not old and new.** Both are current, and neither supersedes the other.
  - **v1 `/signalk/v1/api/tracks`** is a **spatial query**: `radius` and `bbox` filter by the vessel's _last_ position — "which vessels are near me now". Situational awareness and collision avoidance; this is what Freeboard uses. It is the one thing the core v2 History API cannot answer, since that has no spatial predicate, and it's the reason this plugin exists as more than a cache.
  - **v2 `/signalk/v2/api/tracks`** is a **track query**: `bbox` matches when _any_ position within the window is inside the box, or a line between two of them crosses it — "which tracks passed through this box" — served through the provider registry with fan-out and `providerId` stamping.
  - The last-position rule is therefore **correct for v1 and wrong for v2**. `TrackParams.intersects` selects between them and is set only by the v2 provider; do not "fix" v1 to match v2.
- **Both entry points read the same store.** The v1 routes and the v2 provider read the same rows, with the same deleted spans moved out of them, and neither asks a history provider. What each returns of them still differs by purpose (v1 matches the last position and leaves imports out; v2 matches any position or crossing line and lists imports beside the recording), but a change to what one reads that silently leaves the other behind makes the plugin contradict itself depending on which route a client happens to use.
- **A vessel's name and a track's label are two different things.** `contextName()` returns the **bare** name (`Ariadne`) and is what the v2 `contextName` property carries — its spec says "Name of the vessel, aircraft or other context, where known. _Not a name for the track itself_". It resolves `name` and nothing else — matching the server's own `findContextName` in `packages/server-admin-ui/src/utils/pathKeys.ts` — and is **undefined** for a vessel that has not sent one. An MMSI is how a vessel is addressed, not what it is called, so it never appears here. `trackLabel()` returns the **display** label (`Own Ship`, `AIS Ariadne`) that v1's `name` carries, the convention TimeZero's GPX exports use; it falls back through the MMSI to the raw context, because a label always has to render something. The two therefore differ for an unnamed vessel by design — v1 says `AIS 987654321`, v2 omits the field — and that is not the plugin contradicting itself. Do not collapse them: putting a decorated label in `contextName` breaks the v2 contract, and stripping v1's label makes a track list unreadable. Both resolve per request, because an AIS static report can arrive long after the first position, and both accept a vessel's `name` as a **bare string** (how the full data model holds it) or a `{value}` wrapper (how deltas carry it). `app.getPath` is optional — older servers fall back to the MMSI.
- **Imported tracks are a separate kind of track, not a write into the recording.** `storeTrack` keeps a client's track in its own tables (`imported_tracks`, `imported_points`) under an `imported:<uuid>` id; a recorded track's id is `recorded:<context>`. An import is listed by v2 alongside recorded tracks, filtered on its own points and clipped per posted segment, but it is never pruned by either retention, and never returned by v1. Storing and deleting are acknowledged writes outside the recording budget (`docs/history-and-storage.md`), so an import can neither pause nor stop recording. A timed import of the own vessel is the exception (`keepTrack`): it is the boat's own passage, so it is written into the recording, and the answer is `recorded:<context>`. By default (`onOverlap` `keep`) it only fills stretches where the recording has no position for at least `MIN_FILLED_GAP_MS` (`fillGaps`): filling every pause would interleave two sources and draw a sawtooth. `fillTrack` judges and writes it in one store write, binning nothing, so another upload or a restore cannot land in a gap between a read and the write. With `replace`, `recordTrack` bins what was recorded over each segment's span first, and with a history provider installed keeps the entry even where nothing was recorded (`importable`), so the history import does not draw the old passage beside it. The Track API's `storeTrack` always keeps, until the API carries the choice. An import with neither times nor a context is kept: no time window or vessel query matches it, but the plugin route `GET /plugins/tracks/imports` lists every import, and `getTrack` returns it by id. A GPX upload goes through a plugin route rather than the v2 API, because the server parses only JSON and form bodies. The webapp also lists every import through a plugin route, whatever its time span, because its windowed v2 query never matches an old or untimed one; servers older than the Track API's write routes name tracks without their provider prefix, so the page matches its rows on the track id without the provider prefix.
- **A large GPX file of the own vessel goes in slices, and resumes from a checkpoint.** One request caps at `MAX_UPLOAD_BYTES` and the whole file would be held in memory, so the webapp scans the file in chunks (`public/upload.js`, a tag scan that only lists the tracks to choose from) and sends it in slices to `/plugins/tracks/imports/upload` (`gpxUpload.ts`). `GpxReader` reads them with saxes, a streaming parser, keeping the same rules as `fromGpx` (a test compares the two across slice sizes). After each slice it notes a checkpoint: the byte offset of the last point between structural elements and the `<gpx>`/`<trk>`/`<trkseg>` tags open there. `saveGpxUpload` writes the slice's points and that checkpoint in one store transaction (`gpx_uploads`), so after a failed write or a restart the upload goes on from the checkpoint by feeding a new parser those open tags, and the client resends from the offset the server reports. Only the own vessel's timed tracks go this way, written into the recording as `keepTrack` writes them: an import is read whole by every query, so another vessel's track stays within the one-request limit. Each slice is judged against the recording as it was before the upload, as a whole upload is: with `keep`, a segment that runs on across slices is not judged against what it filled in the slices before (`filled`); with `replace`, only time no segment of the upload has replaced yet is binned (`replaced`), into the one recycle bin entry the segment began (`binRecorded`'s `into`); and a day a slice wrote simplified, the next goes on simplifying while the day holds nothing else (`simplifiedDays`), so `simplifyStored()` never simplifies it a second time. One upload runs at a time, and a slice holds it (`reserve`) from before its body is read until it is written, so two requests never buffer a slice each; one left idle for `IDLE_TIMEOUT_MS`, a slice stuck on its way included, gives way to a new one, and is `supersede`d so a slice of it still arriving cannot write over the new upload's row. The client resumes an upload only for the same `fingerprint` (time of change and a hash of the file's ends), since the server cannot see the bytes before its checkpoint again.
- **A delete moves points to the recycle bin; it never drops them.** `deleteTrack`/`deleteTrackSpan` move rows into the `binned_*` tables, so every store read stays unchanged, and restoring moves them back. Recorded tracks are deletable too, which needs one more step: the History API has no delete, so the history import would refill the window. Each recorded entry is therefore also a deleted span (`deletedSpans()`), which the import leaves out, and it outlives the purge of its points as a tombstone, or purging would let the import bring it back. A delete of the own vessel with a provider installed keeps its entry even where the store held nothing (`importable`). A whole delete of a recorded track ends at now: the recording goes on. The bin is purged in `prune()` after `recycleBinDays`, outside both retentions, which must never reach into it.
- **Thinning and simplification are different operations.** `thin()` decimates by _time_ — one point per N milliseconds, whether the boat was turning or holding a course. `simplify()` (Douglas-Peucker, `simplify.ts`) decimates by _shape_, keeping the points that carry the geometry. A route conversion needs the second: thinning 5,550 recorded points to 30 gives 30 evenly spaced positions that miss every turn, while simplifying to 30 gives the turns. In the v2 provider simplification runs **after** thinning, and `epsilon` implies `simplify` per the spec; `simplify` alone derives a tolerance from an extent — one part in a thousand of its diagonal, with a one-metre floor so a vessel swinging at anchor still collapses. The extent is the query's `bbox` when there is one, as the spec's "a tolerance suited to the size of the box" requires, so a viewer's detail follows its zoom; without one it is the track as thinning left it, measured before simplification because the post-simplification extent is what the tolerance produces. A `bbox` without `simplify` simplifies nothing. It is derived from an extent at all because a fixed metre value cannot suit both an ocean crossing and a marina approach.
- **Significance levels let a read at a tolerance skip what simplifying drops.** `significance()` (`simplify.ts`) gives each point the tolerance below which `simplify()` keeps it, all tolerances in one pass: the point a segment splits at does not depend on the tolerance, only whether the split is taken, and `simplify.test.ts` pins the two together. A position's level is floor(log2(significance / 0.25 m)). `refineLevels()`, run in the worker in a transaction of its own every 10 s, and every second while a call leaves work, refines whole UTC days once they ended more than `DETAIL_KEEP` ago, and again when detail thinning reaches one later, in pieces split at recording pauses longer than `CLIP_STRETCH_GAP` and cut at `LEVEL_PIECE_MAX`, about `refineBudget` positions per call, each day counting `REFINE_DAY_COST` more so many small AIS days cannot make a call long. It copies the positions from level 4 (4 m) up into the `significant` table with their level, and notes in `level_visits` the hours each context had a position in each cell of a hundredth of a degree. Refining never writes `positions` or its indexes, which keeps a call to tens of milliseconds on a Pi; only the storage simplification below, which the same call goes on to once nothing is left to refine, deletes from them. `level_frontier` holds each context's last refined day. A day after it, or one in `level_stale`, is read from `positions` in full, so what `significant` holds of a day not refined only ever repeats rows. **Every write that changes the positions of a refined day must call `invalidateLevels()`**, which takes the day out of `significant` and `level_visits` and queues it in `level_stale`; its doc lists the writes that call it. Without the call, a read at a tolerance can draw a position that is gone or leave out one the change made significant, and nothing fails until someone compares the drawn track. The v2 provider passes `tolerance` to the store when it is known before the read: the explicit `epsilon`, or the one `simplify` sizes to the box. It passes none where what follows the read judges a track by the points it is given, since a level leaves out what lies between them: while tracks split at pauses (`segmentGapMinutes`), and for a box without `clip`. The store reads the levels from floor(log2(tolerance / 0.25)) up, in `getTimed` and in a named vessel's box read (`nearBoundsByLevel`), each day from `significant` or `positions`, and the window's first and last positions as well. The box read finds a vessel in the box by `level_visits`, because what a level keeps there can be no position at all, only a line across it, which the clip draws (`clipToBounds`). It marks a stretch read apart from the one before `breakBefore`, as `rowsNearBounds` does. A vessel that comes into the box by less than the tolerance can be left out, since the line the level keeps passes outside it. A box read of every vessel reads no levels. The provider still simplifies what comes back, and `resolution` and `maxPoints` thin what the level keeps rather than every position: the spacing and the budget hold, the points they pick differ. Within one refined piece that equals simplifying every position; clipped and thinned on a boat's store, the drawn track came within 1.6 times the tolerance of every recorded position, where reading every position stays within it.
- **Clipping cuts a track to the v2 `bbox`, before anything else shapes it.** With `clip` on, each stretch inside the box keeps the one point either side of it, so the line reaches the edge, and each re-entry starts a new segment (`breakBefore`, which `thin()` and `segment()` honour). A line between two points outside that runs through the box is a stretch of its own, and a v2 box query matches a track on its lines as well as its points (`createReachesBounds`, and `createMatcher` with `intersects`), so a sparse track, an import with fixes kilometres apart say, does not vanish from a view it runs straight through. It runs before `resolution`, `maxPoints` and simplification, so those spend their budget on what is drawn. The sqlite store reads only the stretches near the box for a clipped query (`rowsNearBounds`); that narrows the read, because the provider does the clipping. A stretch it reads apart from the one before is marked `breakBefore`, which the clip honours, so no line is drawn from one to the other across the box. For a clipped query, and for one that names no vessel, the store finds a vessel by its positions inside the box, from the cell index, so there a recording that only crosses the box between two fixes is left out, which takes a box smaller than the spacing of its fixes; a query that names the vessel and does not clip reads its whole track and matches the line. `clip` absent means a server that predates it, and returns whole tracks.
- **A recorded track too large to answer is read to fit a budget.** Without a window, a v2 query for one vessel is its whole recording, years of positions once the history import has run, and reading it whole to shrink it afterwards (`maxPoints`, simplification) ran a process past 900 MB. So a read without a box first counts each track with `countTimed()`, and one the read would hold more than `MAX_TRACK_POINTS` of is read on its own to fit, as `fitted()` describes; one within it is read and answered as before, `maxPoints` included. The count must be what the read returns: without a resolution it mirrors `daysOf()` from the indexes, and with one it runs `daysOf()` through `keeps()`, the rule `Thinner` keeps by, so a change to `daysOf()` or to thinning has to keep the store test that compares the count with `getTimed()` passing. A fitted track is simplified to at least the tolerance it was read at, or reports the spacing; `maxPoints` asks for spacing, so a track it fits is never fitted to a tolerance. A query with a box is not counted: with `clip` it reads the stretches near the box, and without it a query that names a vessel reads its whole track.
- **A listing reads summaries, not points.** A v2 query with `geometry=false` and nothing that reshapes the points (no box, spacing, budget, simplification or times) takes each track's count, times and bounds from the store's `summarize()`, one pass over the window in the worker, instead of every position copied to the main thread to be counted.
- **A track breaks where the recording stopped, not where its points are spaced.** Thinning spaces the kept points further apart than anything recorded between them. So `thin()` records on each point it keeps after dropping others the longest pause among them (`pauseBefore`), and `segment()` compares `pauseBetween()` with the gap rather than raw timestamps. Code that copies or thins points must keep that field, or a thinned track falls apart into one-point segments ([#133](https://github.com/SignalK/tracks/issues/133)).
- **The webapp is plain static files, deliberately.** `public/` ships as-is and the server mounts it at `/@signalk/tracks-plugin` from the `signalk-webapp` keyword; there is no build step, because a bundler would mean a second build output for a page this size. Two consequences: `public` must stay in the `files` allowlist or the webapp silently vanishes from the published package, and everything the page references must be **relative**, since it is served from a scoped path. It lists tracks from the v2 API — note that API **refuses an unbounded multi-context query**, so the list passes a `duration` — asking for the own vessel's alone first and for the whole list as soon as that request settles, whether it brings tracks, none or an error, or its own shorter wait runs out, so that the own rows show before a month of AIS traffic is read and a stalled request cannot take the list's time (the store answers one query at a time, so asked together they waited behind the list), and links each recorded row to the v1 `track.gpx` route for export (an imported row to the plugin route `/plugins/tracks/imports/<id>/track.gpx`, since v1 never returns imports; it asks for read access through `router.access('readonly')` where the server offers it), because a page with no bundler cannot reach `toGpx` and duplicating GPX serialisation in it would drift from the module. Its label logic duplicates `trackLabel()` because it cannot import from `src/`; `webapp.test.ts` pins the two together.
- **GPX parsing goes through a real XML parser.** `gpx.ts` reads with `@xmldom/xmldom` and writes by hand, because a pattern cannot tell markup from text — a commented-out `<trk>`, or a `<trkseg>` inside CDATA, is text. Two consequences follow. **A document that is not well-formed yields no tracks** rather than the readable half, since returning part of a broken file claims a success it does not support. And **an invalid character reference does not survive a round trip**: the parser decodes `&#0;` into a character XML cannot express, and `toGpx` drops it on the way out. Values are checked on top of the parser, not by it: a coordinate must be an `xsd:decimal` within ±90/±180, a `<time>` must be an `xsd:dateTime` (`Date.parse` alone reads a bare `2024` and rolls `2024-02-30` into March), structural elements must be in GPX's namespace or none, and the Signal K context is matched on its **namespace URI** in the track's own `<extensions>` — never a trackpoint's, or a foreign `<context>` claims the vessel's identity. **Points are sorted by time within each segment** and deliberately not across them, because a segment boundary is a gap in recording. `src/__fixtures__/timezero-seams.gpx` covers TimeZero's overlapping 150-point block seams; the real vendor exports run when `TZ_EXPORT_DIR` points at them and skip when it does not. Coordinates are written at seven decimal places (~11 mm), so a round trip moves a position by at most 5.6 mm.
- **Both single-track routes read through `readTrack`.** The JSON route and `track.gpx` share one pipeline, `TrackStream`, which thins and splits as `segment(thin())` does, so the same window cannot be answered two ways. The JSON route reads the window in one piece. `track.gpx` reads it a day at a time, stepping over days with nothing (`timeExtent()`), and writes each day as it comes (`GpxTrackWriter`): read in one piece, a recording of years was copied whole to the server's thread and then built whole as text, which ran a 600 MB heap out of memory. A store without the optional `timeExtent()` is read in one piece for `track.gpx` too. Export is a route rather than client code for the same reason, and `toGpx` and `GpxTrackWriter` write the same document from the same lines; a test pins the two byte for byte. Without a window the JSON route and the v1 list read the last day (`DEFAULT_WINDOW_MS`), and the list leaves out a vessel with nothing in the window, whichever window it reads: the whole retained track can be years once the history import has run, and building it into one answer ran a boat's server out of memory. `track.gpx` without a window still reads the whole recording, which the webapp's export link for the own vessel asks for, so a request with no window is the one case where the two routes read different windows. Two answers are possible and they are not interchangeable: a **404** means the store does not know the vessel, and an empty **200** means a known vessel with nothing in the window. The store rejects an unknown context with `UnknownContextError`, and the worker carries it across as a flag, as it does `SelfPositionUnavailableError`. While the plugin runs, only that error makes a 404; a stopped plugin answers 404 as well. Any other failed read is logged and answered with a **500**, or cuts a download off once it has begun, so a broken store does not read as a vessel without a track. The v1 list route answers a failed read with 500 too: a list that matches nothing is an empty 200.
- **Contexts are fully qualified.** Positions are accumulated under the context carried by the delta, which for the own vessel is `vessels.urn:mrn:...`, never `vessels.self`. Resolve the `self` alias against `app.selfContext` before any lookup — forgetting this is [#18](https://github.com/SignalK/tracks/issues/18).
- **Coordinate order flips at the boundary.** Internally positions are `[lat, lng]` (`LatLngTuple`); GeoJSON output is `[lng, lat]` via `toLngLat`. The `bbox` query parameter is `west,south,east,north` — GeoJSON order, matching the output rather than the internal one, and swapped to `[lat, lng]` corners as it is parsed. It was latitude-first up to 2.0.2. Check which side of that boundary you're on before "fixing" an order that looks wrong.
- **The own vessel's spacing follows `navigation.state`, and only detail finer than the track resolution is thinned later.** `newPosition` takes a `resolution` per fix: for the own vessel from `stateResolutions` (default `anchored` at 1 s), for every other vessel from `otherVesselsResolution` (the track resolution unless set), whose transponder state is too often stale to follow. The sqlite store notes where it recorded finer than its resolution in `detail_spans`, and `prune()` thins what is older than `DETAIL_KEEP` (a day): a span that ended before that back to the resolution, and one still going on to the spacing an anchor alarm reads the whole stay at (`DETAIL_STAY_POINTS`), keeping the span's start so that spacing is measured from the drop. It thins those spans and nothing else; do not replace the spans with a guess from row spacing. That is the store with `storageTolerance` 0. At the plugin's default of 0.5 m, `thinOldDetail` does not run, and the simplification below takes its place.
- **Stored positions are simplified once refined, and the levels stay as they are.** With a positive `storageTolerance`, once `refineLevels()` has nothing left the same call goes on to `simplifyStored()`, which deletes the positions of refined days that `simplify()` at that tolerance leaves out, for every vessel and for what imports wrote into the recording, since a day imported at one second weighs on every read as much as one recorded at one second. It keeps one at least every `STORED_GAP_MAX` (60 s) where the recording had one, so a straight leg never reads as a pause to `segment()` or as a gap to `fillGaps`, and every position `significant` holds. It needs no `invalidateLevels()`, the one exception to that rule: what it deletes lies below every level, and simplifying what remains to any tolerance from this one up gives what simplifying every position did (`storedKeep`, and the store test that pins it). Each context has its own frontier in `simplify_frontier`, with the tolerance it was reached at, so a raised tolerance goes over every day again, and a change to a simplified day queues it in `simplify_pending` for after its levels are rebuilt. An import is simplified before it is written instead, on each day `simplifyStored()` will go over that the recording holds nothing of (`simplifyUnrecorded`): it writes what simplifying the day would leave, cut into the pieces refining cuts it into, so that deleting most of it a day later does not cost an SD card the writes a second time. A day the recording has positions of, an earlier import's included, is written in full, since simplifying part of a day is not simplifying the day; the runs of one upload are judged together and written in one go for that reason. Such a day is noted in `simplified_days` with how many positions it kept, and `simplifyStored()` passes over it while it still holds that many: simplifying it again would cut its pieces where what is left falls, not where the import's did, and drop their ends. What it deletes is gone: the docs tell users to archive a copy if they want every position.
- **`throttleTime` thins on the leading edge.** A burst of positions inside one `resolution` window contributes exactly one point, and the rest are dropped, not buffered. Tests that feed positions synchronously see a single point unless they advance fake timers past `resolution`.

## Code quality

- **Scope discipline.** Make only the change requested or clearly necessary. A bug fix doesn't need the surrounding code cleaned up.
- **Self-documenting code.** Comments explain _why_, not _what_. No echo comments.
- **TypeScript with real types.** Avoid `any`; prefer `unknown` plus narrowing at the boundary. Prefer a pure, testable helper in `utils.ts` over logic inlined in a route handler — that's what makes it reachable from `utils.test.ts`.
- **Tests.** New behaviour needs a test in `src/*.test.ts`. Test behaviour, not implementation.

## Contributing

- **One logical change per PR.** Refactors and behaviour changes go in separate PRs.
- **Angular conventional commits:** `<type>(<scope>): <subject>` — `feat | fix | docs | ci | chore | refactor | test | perf`. Imperative, no trailing period.
- **Releases are cut by release-please.** Every releasable push to `main` updates a standing release PR titled `chore(release): X.Y.Z`; merging it bumps `package.json`, creates the tag and the GitHub Release, and `.github/workflows/release-please.yml` then dispatches `release_on_tag.yml` on the tag to publish to npm. The version follows the commits: `feat` → minor, `fix` and other releasable types → patch, `!` or a `BREAKING CHANGE:` footer → major; a `Release-As: X.Y.Z` footer overrides it. Do not bump the version in an ordinary PR. Pre-releases (`-beta.N`, `-rc.N`) are still tagged by hand, and `release_on_tag.yml` creates their Release itself.
- **A push with nothing releasable does not touch the release PR.** A gate in `.github/workflows/release-please.yml` decides what counts; its comment lists the cases. Two rules follow from it: revert with a conventional `revert:` subject, since release-please ignores GitHub's `Revert "…"`, and change the gate's last alternative together with `pull-request-title-pattern` in `release-please-config.json`, or the release PR's merge never creates a tag. Dependabot scopes its commits (`build(deps)`, `build(deps-dev)`, `ci(deps)`) so the gate can tell a runtime bump from the rest.
- **PR titles become release notes.** release-please asks GitHub to generate the notes from merged PR titles and their authors, so write the title as the line you'd want a user to read in the changelog. There is no CHANGELOG file to maintain.
- **Labels group the release notes, and the PR title sets them.** `.github/release.yml` maps labels to sections; `.github/workflows/label-by-title.yml` labels each PR from its title's type when it is opened or retitled; its header comment is the mapping. A label set by hand places a PR the same way until its title changes; an unlabelled PR still appears, under Other. The version never depends on labels. A PR merged without a label can be labelled afterwards; run the release-please workflow by hand to rewrite the standing release PR's notes.
- **Branch from latest `main`.** Hyphens in branch names, not slashes.
- **CI must be green.** `.github/workflows/signalk-ci.yml` calls the canonical `SignalK/signalk-server` reusable workflow across Linux x64/arm64, macOS and Windows on Node 22 and 24, and its `e2e` job runs `npm run test:e2e` against signalk-server from npm.
- **This file is the review baseline too.** `.coderabbit.yaml` points CodeRabbit here rather than restating the conventions, so a rule added below applies to automated review as well. If a review comment contradicts this file, the review is wrong — or this file is out of date, which is itself worth fixing.

## Traps worth knowing

- **`main` is load-bearing, despite `exports`.** The Signal K server resolves an installed plugin _by directory_ ([`importOrRequire`](https://github.com/SignalK/signalk-server/blob/master/src/modules.ts)). Node's CJS directory resolution reads `main`, not `exports`, and so does the server's `esm-resolve` fallback — with `exports` alone the resolver returns `undefined` and the plugin fails to load with a bare `MODULE_NOT_FOUND`. Keep both fields pointing at `dist/index.js`.
- **`engines.node` is `>=22.5.0`, and two separate things pin it.** ESM-only needs 20.19, the release where `require()` learned to load ES modules; below it the server's loader path cannot reach this plugin. `node:sqlite` needs 22.5.0, and the higher of the two wins. The server's own floor is `>=22`, so this excludes nothing that could have run the plugin. The reusable CI workflow checks the declared floor against the built-ins actually imported and **fails the build** on a mismatch — so adding a newer built-in means raising `engines.node` in the same PR.
- **The plugin must keep a default export.** The server's `import()` fallback returns `module.default` with no `?? mod`, so a named-only export loads as `undefined`.
- **The Signal K server runs express 4.** Route patterns use express 4 syntax — a bare `*` wildcard, not express 5's `*splat`. Pin `@types/express` to v4 so the types match the runtime.
- **`files` is an allowlist, and it is short.** `dist/`, `public/` and the icon — nothing else. The package once shipped at 174 MB unpacked because a denylist `.npmignore` failed to exclude `node_modules`. Dropping `public/` is the opposite failure and just as quiet: the plugin still works and the webapp is simply absent. Verify with `npm pack --dry-run` — expect a few dozen files and tens of KB, `public/` among them.
- **`connectable()` resets by default.** rxjs 7 replaced `publishReplay` + `ConnectableObservable`; its `connectable()` defaults to `resetOnDisconnect: true`, which would drop the accumulated buffer when the last subscriber leaves. The explicit `resetOnDisconnect: false` preserves the old behaviour and a test pins it.
- **The README used to document the wrong path for a single vessel** ([#12](https://github.com/SignalK/tracks/issues/12)) — the route is `/signalk/v1/api/vessels/<vesselId>/track`, not `/signalk/v1/api/tracks/<vesselId>`.
